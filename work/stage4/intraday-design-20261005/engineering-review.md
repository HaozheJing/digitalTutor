# 日内正式承接：最小工程调整评审

2026-10-05。仅方案；核对当前主目录 `backend/src/digital_tutor/`，并参照隔离 K 已有候选/来源边界。主目录与 K 不是同版：以下未加前缀的行号指主目录。没有改业务源码、业务数据或调用 API。

**结论：可保留 Planner/Service 两角色、三个上下文配方和唯一 JobQueue。需要明确改变的是“只有每日一次可新增正式事项/主动成员”的业务合同：一次 daily baseline 不变，允许受宿主绑定的日内承接修订。不能仅解除 DAILY_ALREADY_COMMITTED，也不能偷偷扩权 progress。**

## 1. 日内请求走 Planner 的承接分支，Service 保留即时服务

推荐流程：Service 核清自然请求、保留原要求与期限 → 持久 PendingPlanningInput → 宿主为该需求建立一次承接任务 → Planner 使用 `planner_daily` 配方判断接纳/已有目标归并/等待补充/拒绝 → 原子保存 Event、计划修订、决定回执及必要执行 Job → Service 依据真实接纳回执告知并执行。

- 普通问题仍直接答复，不新增 Planner 调用。只有需要未来履行的独立责任才申请正式承接。Service 的“我已记录”与 Planner 实际接纳必须分开，不能在承接结果前保证已安排。
- 保留 `planner_daily` 名称作为计划/承接配方；增加宿主绑定 `planning_reason=baseline|admission`（名称可调整），以及本次允许处理的 pending ID/版本、业务日、原计划修订号。模型不能自己选择理由或扩大需求范围。
- 这是**新增业务触发原因和受控提交权限**，不是第三个 Planner 角色或第四个配方；旧文档“只有 daily 新增”的表述需明确更新为“baseline 或已授权承接修订可新增”。不能以复用函数名掩盖合同变化。
- `planner_progress` 不变：精确 report/revision、原 Event IDs，只改原事项的进展/下一步/等待/完成，不接独立新需求、不新增日内成员。参见 `planning.py:131-153`、`context.py:58-69`。
- 现 `record_pending` 仅记账，未创建承接任务（`application.py:180-189`）；新接线应让需求与触发身份原子落库，去重依据是原需求/明确修订身份，不是模型每次生成的新 request_id。baseline 若已处理该 pending，排队承接任务必须在领取前识别实际决定并无模型结束，不能再接一次。

### 接纳结果通知必须有独立的恢复依赖

Service 已解释请求并登记 pending 后，“是否接下/何时安排”的意图仍待答；不能为了放行 Planner 假填最终回复，也不能让最高优先级 service 因一般 unanswered/family_version 扫描反复被领取。应在**原 service continuation**绑定 `等待指定 pending 身份/版本的正式决定`，claim 在决定尚未存在时直接跳过（零模型），释放家庭执行权让 admission/baseline 处理；不是睡眠占 lease。

Planner 的正式接纳、拒绝或需补充决定原子落库后，才给原 service 恢复资格；Service 读取实际结果，以授权待答 reply_scope 回复，真实回执才结清“决定通知”意图。Planner 不自己向家庭发送。决定本身与通知送达是两本事实：发送未知只恢复原 operation，不重新调用 Planner 承接。

技术失败/REPORTS_PENDING 不伪装成正式决定：保持需求与通知责任，给出可见阻塞 owner/有界恢复，必要的状态说明也不能结清原决定意图。新的**未解释**来信仍可抢占旧规划；相关更正必须使原 pending 决定依据失效或产生明确修订，不能让旧版本结果去回答新版本请求。单纯已解释、等待指定决定的旧意图，不得反过来阻止负责产生该决定的 Planner。

## 2. 一个 baseline，多次有依据的修订，一个有效视图

保留 `plans(family_id,business_date)` 唯一行和稳定 plan_id，保留原始 baseline；新增不可变修订记录/版本及有效视图。可复用现 records/history 存储，不必建立第二套计划引擎。基线成功后只允许 admission 类型提交小范围增量，不能再次作为 baseline 整份覆盖。

| 提交类别 | 应允许 | 必须拒绝 |
| --- | --- | --- |
| baseline | 全责任目录决策、当天基线成员/顺序 | 同日第二次 baseline |
| admission revision | 处理绑定的新需求；同目标沿用；创建获准责任；追加当天合格成员并确定其位置 | 修改未授权原目标、静默抹掉旧成员/未知操作、凭空扩责任、跳过未消费报告 |
| progress | 更新报告绑定原事项及其当前执行状态 | 新建正式事项、把原未选事项偷偷加入今天主动范围 |

最小事务门禁：expected_family_version + expected_plan_revision + pending source/version + 同目标唯一性 + 来源/材料权限 + 每个新/受影响有效成员有动作或真实等待；Event/修订/需求决定/回执/排队意图全部成功或全部回滚。初版建议承接也保留本家庭 REPORTS_PENDING 门禁，先消费再取新快照；不能只保留 baseline 门禁而让 admission 从旁绕过。代价是失败报告会延迟新承接，需可见原因与明确处置 owner。

现有改点：`planning.py:77-129` 对同日一律拒绝且只创建新 plan；`jobs.py:165-174` 看到任意今日计划便判 daily 已完成；`scheduler.py:93-96` 同样只凭计划存在确认完成。三处必须按 baseline/admission 的**具体成功回执/目标修订身份**判断，不能看到 baseline 就吞掉后续承接任务。

`context.py:97-120` 应给承接分支当前有效计划及 revision、绑定需求、完整未完责任和未消费报告，避免重复建目标。主动发送读取同一有效视图；当前 `send_policy.py:51-52` 取当天列表第一份计划的逻辑不能演变为从多个修订随意取第一份。

## 3. 时间、期限、排序分别负责什么

| 字段/概念 | 建议语义 | 不可用来替代 |
| --- | --- | --- |
| Event.due_at / deadline | 原责任的履约截止，延期须保留原约定/有效接受证据 | 不是任务开始时间，不意味着到截止才启动 |
| Step.execute_at | 当前步骤最早可开始的业务时刻，带时区；无值代表其他条件满足即可开始 | 不是截止，也不是精确分钟交付保证；不自动解除暂停 |
| Plan.rank | 同家庭、同一批已到时且有资格工作的优先次序 | 不让未来 rank=1 挡住已到时 rank=2；不能越过主动窗口/权限 |
| Job.not_before（现有） | 技术失败的真实时钟退避 | 不能直接复用为模拟业务执行时间；当前用 lease_clock 比较 |

当前 `domain.py:77-81` Step 无时间字段，`EventCreate:90` 只有 due_at；`jobs.py:144-145` 的 not_before 使用真实租约钟。最小做法是在 Step 明确可选 execute_at，Scheduler 与 claim/最终发送均以业务钟复核；保留技术 retry_at/not_before 独立。若用户给“下午”“四点前”，应保留原精度，不能擅自变成精确预约时刻。execute_at 晚于已接受 deadline 时必须显式暴露不可履约冲突，不暗中延长期限。

现 step_key 包含完整 next_action（`scheduler.py:12-13`），时间修改可使旧步骤失效；但新增默认字段会影响旧模型载荷/回执摘要，必须保持历史 payload/digest 重放兼容，不一律重新序列化补 null。

## 4. 唯一队列中调度未来任务，不按“队首”等待

继续 `JobQueue`；可沿用 kind=daily 并加宿主 planning_reason 区分承接，不必增加角色或第二条队列。baseline Job key 保留 family+date；承接 Job key 使用 family+pending identity/revision，避免同一需求被每次扫描重新生成。

“新事项入队”应表示已持久化调度意图，**不是立即调用模型**。未来 Step 可以在同一队列保持 scheduled/ready 但不具备领取资格，或由其持久 Event 到时派生同一 Job；两种实现只选一种权威事实，不能两边各维护一套独立待办。建议沿现事件派生方式，Event/Step 是计划权威，队列仅承接可恢复的执行身份；展示未来安排可直接读 Step，不必用模型轮询制造 Job。

领取顺序必须先筛资格，再排序：依赖已解除/未待更新/业务时间已到/当天有效主动成员（仅主动联系类）/窗口及暂停/原未知操作 → 在合格集合按任务类型、家庭公平性、rank、到时时刻等有界选择。不要 pop 最早未来任务后 sleep；当前 `claim` 已逐项 continue，不是只取队首，可在原选择器扩展（`jobs.py:110-180`）。

- 当前排序只有 kind 优先级+rowid，未读 plan.rank；`scheduler.py:31-44` 也是 Event 存储顺序。需加入明确排序合同，不能只往计划写 rank 就宣称按事项时间执行。
- 若决定提前持久化未来日 Job，当前 `jobs.py:141-143` 对“不等于今日”一律 expire 会误杀未来任务，必须区分过去/未来：过去资格过期，未来跳过。更稳妥的是只到目标日再派生，仍保留 Event 的未来安排。
- 跨日到时不自动继承昨日主动资格：当天 baseline/承接有效计划须明确选入，再允许主动执行。已正式接纳的跨日承诺必须完整进入次日 Planner 上下文；若不选入，需明确阻塞/延期处理，不能责任还在而无人推进。
- 内部 verify/review 可以按原目标核实，不能把今日主动成员要求误套到所有内部动作。主动发送仍重新检查有效 plan revision、时间、暂停、回执和原目标；已有 unknown 必须先查原 operation，不因为计划修订改个 Job ID 就再发。
- 新来信仍撤旧能力、家庭内串行，承接不能抢占已撤权但尚未退出的进程；多家庭公平仍需在唯一队列解决，禁止靠跨家庭串行等待一个未来时刻。

## 5. 待决风险与建议默认边界

1. **承诺何时生效**：建议 Planner 原子接纳回执成立才算正式承接；通知渠道未知不抹掉内部承接事实，也不能重复承接/重复发送。对已过期或容量不足需求，保留原期限并明确未接纳，不先承诺后排队。
2. **允许多大日内修订**：建议初版只处理绑定新需求、追加成员/插入次序，不开放整天重排、撤销或挪动其他已承诺任务。更大范围调整需明确业务授权。
3. **baseline 之前/夜间请求**：若尚无当日 baseline，先按既定窗口和报告门禁完成 baseline，再承接；若要夜间立即正式接纳，这是运行窗口的另一个明确选择。接收请求可以全天，正式接纳与对外联系应分别说明，不能暗中扩大 08–21 外发窗口。
4. **报告长期失败的承接阻塞**：保留门禁的初版会延迟该家庭新承接。应设可见待处理状态与受限修复路径；不要“只读一下旧报告”就绕过消费合同。
5. **到时/截止风险与容量**：rank 不能保证 SLA；同家庭频控、执行时长、模型重试和人工材料缺口都可能使时间不可满足。最小承接评估应检查已知冲突并如实等待/拒绝，不能默认所有请求都接。
6. **版本与重放**：baseline 唯一、admission 重复、pending 来源更正、同目标归并、旧 receipt、跨午夜恢复、旧 queued/unknown 操作都要有稳定身份。先修已定位的报告剩余表达与派生消息版本阻塞，日内承接不能在这些欠项之上宣传持续链已通。

本轮推荐的是有限新增承接合同，仍复用 Hermes 原生有限运行及工具循环；不修改 vendor，不增加通用工作流/任务队列。实施前应将旧“今日成员永久固定”改为“baseline 固定、授权修订留痕、当前有效视图唯一”，并明确该项是用户已选择的新业务能力，而非对旧验收结论的改写。
