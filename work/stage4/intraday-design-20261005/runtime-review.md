# 日内正式承接与按时执行：运行边界审查

2026-10-05。只读设计，未改代码、未运行模型。基于隔离 K、前次 Hermes 调研及持续运行审查。**用户选择日内正式承接，是对原“只有 daily 新建正式事项和确定主动成员”的业务合同调整**，不能伪装成旧合同已覆盖的小提示词修复。仍保留两角色、三个配方、原生 AIAgent harness 与唯一 JobQueue。

建议：Planner 负责有依据地承接、决定具体下一步及执行时间；宿主按时间与状态决定是否有运行资格；service 到时执行、保存真实报告；progress 更新原责任。既有 Goal 是长期完成标准，Plan 是每日工作视图，一次排期只是原 Goal/交付义务的一个步骤，不能把三者合并成一个 completed 状态。

## 1. 当前源码不能直接满足“按时间执行”

- `domain.py:79-82` 的 Step 只有 action_kind/target_refs/purpose，**没有执行时间**。Event.due_at 是事项期限，不是步骤开始时间。`scheduler.py:38-43` 看到 next_action 就入队，且 job key 含当天日期。因此只让模型把“明日下午”写进 purpose 会立即入队；同一步跨日还会生成新的日 key。
- `planning.py:76-84,127-136` 每家庭每日只能成功提交一次 Plan，成员保存为 event_id/rank；`planning.py:160-164` 明确 progress 不改成员。现日内新需求只能 pending，不能可靠承接当天新正式事项。
- `send_policy.py:52-56` 主动发送只认当前日期的 Plan.items。仅保存未来 Event 不足以让明日执行；依赖次日 daily 再次选中，会把已承接承诺变成可能丢失的候选。
- `jobs.py:140-142` 旧 business_date job 过日过期；当前下一步身份和排期身份未分开。旧日期授权不能直接延长。
- 当前还存在已识别的“入选成员缺执行入口”、报告省略剩余语义、消息派生版本妨碍报告消费等问题，须先一并补合同，不能在其上宣布闭环已经成立。

## 2. 推荐闭环与角色权限

| 环节 | 谁做 | 生效条件与结果 |
|---|---|---|
| 新需求 | service | 读真实来信、定位原事项，保存结构化待承接输入及真实来源；不直接新建正式 Event，不把登记说成已承诺 |
| 局部规划 | Planner | 规划配方新增明确 `intraday_admission` 触发分支；仅处理本次绑定输入/规范候选及相关原事项，读取全家庭冲突摘要 |
| 承接提交 | 既有业务事务 | 同目标沿用；原子保存正式责任、下一步、排期授权、来源/时间精度、必要当日视图修订及输入决策；返回真实承接标识 |
| 承接确认 | service | 只有提交已生效才能如实确认具体承接内容；通过原消息未答/续办责任进入同队列，不由宿主替模型写回复 |
| 到时执行 | 宿主→service | 宿主选出到时步骤，fresh run 绑定家庭/Event/步骤版本，重新检查当前限制；service自己读资料、做动作、核回执 |
| 执行报告 | service | 保存原 Event 绑定的真实操作/新事实与未完成情况；缺报告不以工具成功直接当闭环 |
| 原事项更新 | planner_progress | 消费绑定 report revision，更新原 Event 下一步/等待/完成；若产生下一步，其新排期也须在原目标与已授权服务范围内 |

仍使用 `service / planner_daily / planner_progress` 三个配方；`planner_daily` 名称沿用，但规划触发必须明确区分 daily_baseline 与 intraday_admission，不能伪造第二次 daily 成功。只在原 JobQueue 增加一种受限规划触发/绑定即可，不新建 Planner 实例常驻、不新增模型循环。是否采用新 job.kind 是实现命名选择，不代表第二队列。

新准入工具与 daily baseline 工具权限应分别绑定：admission token 只允许其输入 ID/版本、相关 Event、目标日期；不能调用全量 daily 重排、不要求对全家庭所有 pending 作处置。普通来信仍只用 service；只有明确需要新正式责任/正式排期才排 admission。progress 不能借报告增加不关联的新需求。

**承接结果必须可被原 service 重新发现。** 若首轮已经回复“已登记”但排期尚未提交，不应误清最终承接答复责任后让后续确认消失；可用当前多意图/partial reply 机制保持该意图未完，绑定 admission 的提交结果变化使原 service 续办。若用户不需要额外确认，则保存可查的内部承接结果即可。不要为了唤醒而造一条家庭来信。

## 3. 跨天承接：持久责任与排期授权，运行能力每次重签

推荐不另造 Agenda 表作为可领取任务。正式承接记录依附现有 Event/步骤（必要的审计修订仍用 existing records），至少区分：

- 原责任身份、requirement_revision、规范目标、来源输入/候选与版本；实际承接的是哪些 lesson/交付 part、何种动作。
- 一个明确的 **step/schedule revision**；执行最早时刻 `execute_after` 与业务 deadline 分开。明确一次性执行，或明确业务规则授权的重复频率；未约定重复不能自动日更。
- 来源原期限文本、精度、时区；“下午”“四点前”不能被无依据精确化为承诺 16:00 整点发送。宿主校验服务窗口、材料/媒体能力及已存在冲突，Planner在可行范围内确定下一次执行时刻。
- durable admission/commitment ID、授权来源、有效动作范围、是否已消费/被后续排期替代及关联操作 ID。**这是业务排期授权，不是跨天复用的能力令牌。**

执行日到来后，宿主从这些记录投影“今日已承接的到时步骤”；它只是把既有事实映射到当前日，不新增事项、不生成新步骤、不替模型做规划。即使次日 daily 尚未提交或因无关报告门禁未成功，原已承接步骤也不会从责任视图消失。其 fresh service run 能否执行仍看本项报告/未知发送、暂停、模式、频控、当前来源及窗口。

发送授权须改为受控的两种来源，不能模糊成“历史计划里出现过就能发”：

1. **普通主动资格**：当前日期有效 daily baseline/合法日内修订选中的当前步骤。
2. **跨日已承接资格**：明确 admission ID + Event/requirement/step/schedule revision + 当前执行时段 + 未消费状态；只限该次承接步骤，并且要求当前授权绑定与正式记录完全吻合。

两类都只能给新 run 发新 lease/capability，最终 prepare/dispatch 重核。持久承接不是绕过新暂停的许可证，也不允许旧 queued 操作在原 run 撤权后继续发起。历史普通主动资格不能转换成第二类；必须有本次正式承接的可核来源记录。

**每日一份日容器可以保留。** 其中“一次 baseline 成功”和“effective 今日视图 revision”分开；已承接步骤作为读时投影叠加在 baseline 上，不一定要提前生成明日 Plan。次日 baseline 应看见这些硬约束，不能通过遗漏成员取消承诺；对普通主动成员仍可取舍。实现可保留日容器晚于已承接投影生成，不必为所有未来日期预建空计划。若 day view 需要持久修订，保存输入/变更/版本即可，不给 view 添加 claimed/lease/retry 字段，以免变第二队列。

这意味着原“当前日 Plan.items 是唯一主动来源”明确改成上述两类可核来源。若仍坚持旧单一门禁，又说已承接步骤不依赖明日 daily，两者在逻辑上不能同时成立。

## 4. 同时多项、插入与改约

同家庭同时间三项不等于三个并发模型。现家庭串行继续保留；宿主按 execute_after、业务优先级/稳定 rank、最后稳定 ID 选择顺序。Planner 应在承接前看现有已承接窗口、剩余工作与频控；不能许诺三个服务都在同一秒完成，也不能用未经验证的模型耗时估算装成硬 SLA。不同家庭可由多个原 Worker 并行，容量不足时不能无限承接不可行期限。

新来信进入时沿用 `yield_to_inbound`：撤旧写能力但暂保留家庭 leased 排他，待原进程结束/有界过期后 service 先处理。局部排期必须使用新 family/event/schedule 版本。旧排期尚未提交或尚未 dispatch，可以以新事实修订、让旧 job 失效；已 dispatch 的动作不能通过改约被“撤销成没发”。

改约分两个概念：内部下一次核查/工作开始时间可以在既有授权内调整；**家庭已承诺的交付期限**必须保留原约定，按现有 proposed_change / acceptance 证据合同确认才生效。不要把重排 execute_after 当作自动接受新的 due_at。原截止已过时，应记录 overdue/需沟通，不能机械挪到明天08:00后宣称按约完成。

部分执行后插入独立需求，只局部承接新项。若它消耗同日共同额度、改变家庭级暂停或排挤已有承诺，必须把这些冲突读入快照并核验；“局部Planner”不意味着可以完全不看全家庭状态。

## 5. 未知发送、报告门禁与失败

同一步存在 queued/dispatching/accepted/unknown operation 时，不因改约、新日期或新 plan revision 再造等价发送。原 operation_id 只读核实；真实新回执/缺结果后才走有限内部恢复，补报告并由 progress 处理。排期可以对未来未发步骤作变更，但不得将不确定副作用覆盖掉。家庭仍可答新的普通问题。

最小可靠首版建议保留既有 **全家庭报告门禁用于 Planner admission 的正式提交**，先由原 progress 队列处理，再重新取 admission 快照。service 可先登记新需求，不得在门禁尚未过时宣称已正式承接。这样不新增“哪些历史报告绝对无关”的复杂依赖判断，也要求先修现消息派生版本导致的消费阻塞。

已承接到时执行则至少阻断本 Event 的 update_pending/未知发送；不能因无关责任的一份报告让所有既有承诺无限静默。现 service发送已有本 Event.update_pending 校验，但同家庭权限/额度变动仍须核当前事实。若需求是“即使全家庭其他报告未消费，新需求也必须当场正式承接”，那就要另行做依赖作用域与共享约束证明；不能直接删 REPORTS_PENDING 守卫称为最小补丁。

admission 工具提交成功后模型进程失败，重试必须命中同一 receipt，不能再建事项或重复确认；发送成功但报告未落则保留原 operation，通过现 recovery_only 补账，不重做已发送动作。无新可运行事实的等待不触发 LLM；失败仍有界退避，不能按到时 tick 永久重试。

## 6. 防重、版本与上下文投影

| 对象/视图 | 建议约束 |
|---|---|
| admission 身份 | 家庭 + 原需求/候选 ID + 原需求修订；提交 request_id 幂等，摘要包含非空排期与责任字段 |
| Event 身份 | 保留规范 goal_key/课程版本/原目标映射；相同目标沿用原 ID，新增请求不靠改名绕重 |
| 步骤身份 | 稳定 step revision；排期修改带 schedule revision，明确旧 job superseded；不能仅拼 today 让跨日自动再发 |
| 执行 job | 同一家庭/Event/step/schedule revision 只有一个可执行实例，仍落原 records.kind=job；日期只是业务窗口，不是默认重复次数 |
| 副作用身份 | requirement revision/part/purpose 等明确关联，未决 operation 必须被新快照看见；新排期不能改变同一副作用的幂等身份 |
| Planner快照 | 最新 family version、相关 Event/候选/输入/源指纹、已有承接窗口与配额/暂停摘要、原日 baseline与当前视图revision |
| service快照 | 只给当前家庭当前步骤、执行时窗、授权来源及有效范围、原目标/剩余、相关报告/操作/来信；不倾倒所有家庭计划 |
| progress快照 | 精确绑定报告及原 Event集合；有原剩余/完成标准、已承接期限、当前步骤及未决operation，不因一份报告扩权限 |
| 日视图 | 只投影当前有效步骤；显示来自baseline还是accepted commitment、为何等待/阻断/未入选；旧版本保留审计 |

family version 仍是并发提交保护；来源内容指纹负责区分真实更正与消息回执附加，二者不可互相替代。修改另一个事项会让旧 family snapshot 重取，但不应使未变化的同一到时授权生成新模型调用。

## 7. 最小文件级工作范围与反例

不改 vendor。业务变更集中在 `domain.py/planning.py`（显式承接与时间/版本合同）、`application.py/tools.py`（受限提交与幂等）、`context.py/runtime_assembly.py`（触发与投影）、`jobs.py/scheduler.py`（原队列绑定与到时领取）、`send_policy.py/outbox.py`（最终授权与原副作用核实）。复用 existing records 和 receipts；若新增小型排期校验模块，其职责仅为时间/授权投影，不引入 DAG、阶段引擎或第二任务状态机。

必须用以下反例检验设计是否真成立，而非只看“生成了计划”：

1. 今天10点承接明天16点，今天不执行；明日daily未运行仍能发现原承接，但新暂停会阻止发送。
2. 昨天普通daily选过的事项没有正式承接，今天不能靠历史Plan外发；已承接也不能每日无穷重发。
3. 同家庭同一时刻三项串行，旧run被新来信撤权后不能与插入任务重叠写；另一家庭不被无关租约锁住。
4. 改约发生在queued、dispatching、unknown、sent四个阶段，分别核授权失效/原号核实/补账，不统一当作可重试新发送。
5. admission已提交而模型退出，重试返回原事件/原排期；确认回复已送但无outcome，内部恢复不能再确认一遍。
6. 当天已有baseline后正式承接两项，baseline仍一次，日内修订有版本；次日baseline不能遗漏即取消硬承诺。
7. “下午”“四点前”保留原精度；跨日/过窗/不可行媒体不能被工具默认值捏造成精确可交付承诺。
8. 同目标新增请求、部分报告、原消息派生版本变化、源真实更正分别处理，不能靠清报告/换ID/删操作让流水线畅通。

以上是拟调整合同与最小实现建议，不是 K 已有能力或新验收结果。正式实施前需将“持久承接授权 + 日baseline及日内修订”的规则同步主方案、接口合同、metadata与程序/语义验收；无需重写 Hermes harness。
