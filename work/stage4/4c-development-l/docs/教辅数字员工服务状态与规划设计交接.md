# 教辅数字员工服务状态与规划设计交接

更新日期：2026年10月2日  
适用项目：少年得到阅读营数字员工第二阶段  
讨论范围：单个孩子及其家庭，业务设计和流程模拟  
文档状态：已确认原则与 baseline 建议；不是已冻结的后端接口或数据库设计

本文供下一会话和接手智能体使用，集中说明需要维护哪些信息、信息之间如何衔接，以及哪些问题尚未确定。当前最重要的结论是：**回复独立即时处理；Event 保存持续事项；DailyPlan 保存今天的安排和实际结果；当前执行列表根据最新条件生成。等待的事项保留记录，但不占执行位置。**

本会话只做方案梳理。后续具体实现由项目负责人另行派发。已经完成的 HTML 是业务演练，不能据此认定真实模型、业务接口或长期运行机制已经开发完成。

## 1 项目背景和当前范围

数字员工需要结合学习事实、历史沟通、企业知识和家庭个性化信息，承担原来教辅老师的大部分工作，包括课程答疑、互动、督学、反馈、资料准备和跟进。打电话等已明确由真人完成的工作，仍由真人执行，智能体负责协调和记录结果。

当前先围绕一个孩子设计，先跑通后端服务机制，再考虑前端。不要提前扩展为多学生调度、复杂任务依赖图或完整全年自动化系统。

项目负责人已选定 OpenViking 作为知识库与上下文组织方案。Hermes 是倾向采用的智能体框架，最终版本、部署方式和是否正式采用仍待落实。本文不把这些技术选择视为已实现。

业务理解如下：

- 每周一次一对一点评主要对应服务动作表 2.3 的互动流程，包括教师发起、孩子表达、教师具体回应。
- “随时请教的老师”同时承担产品服务问题和孩子的学习问题。
- 服务动作提供目标、条件、边界和参考方法。同一个动作面对不同孩子，可以有不同内容和落实方式。
- 个性化信息来自日常服务中的自然发现，当前不额外增加主动调查兴趣、偏好等动作。

## 2 已确认的设计原则

| 原则 | 具体含义 |
| --- | --- |
| 回复永远优先 | 家长或孩子有问题，直接进入即时响应，不作为 DailyPlan 的一个任务等待排序。孩子表达后的反馈也走即时响应。 |
| 触发只是评估入口 | 规则命中、到达时间、新学情出现，只说明值得检查，不等于必须联系或发送消息。 |
| 一个事项跨日接续 | 补课、互动、真人服务等沿用原 Event，不因日期变化重新创建或重新发送。 |
| 等待不占执行位置 | 当前没有可做的一步，就离开当前可执行列表；原事项、等待条件和已做记录继续保留。 |
| 排序只在可执行工作之间进行 | 重要、紧急或今日必办，不能让缺少条件的工作自动变得可执行。 |
| 今日目标与事项完成分开 | 周五邀请已发送，可以达成周五目标；整个互动要等孩子表达并得到反馈后才可能完成。 |
| 合并消息不混同目标 | 表扬与互动可以合并成一条消息，但分别按各自标准判断是否完成。 |
| 事实和推断分开 | 完课支持参与行为描述；理解、表达、迁移等判断需要相应作品和证据。 |
| 时间保留真实精度 | 已知时间明确到具体月日时分，带时区；没有给出的时刻保留未知。 |
| 发送以实际结果为准 | 草稿不算已发送；发起不算成功；结果未知先查原回执，不盲目重发。 |

## 3 需要维护的信息总览

“两类主要业务记录”指 Event 与 DailyPlan，并不意味着整个系统只允许两张物理表。长期记忆、聊天记录、发送回执等仍需要可靠保存；已有业务系统能够提供的记录，优先查询和引用。

| 内容 | 保存什么 | 与其他内容的关系 |
| --- | --- | --- |
| Event 持续服务事项 | 目标、来源、相关课节、当前进展、下一步、等待与约定、实际结果、历史变化 | 服务是否结束的主要记录，跨日沿用 ID。 |
| DailyPlan 当日规划 | 今天准备推进哪些事项、各推进到什么程度、建议顺序、已完成的当日工作及依据 | 引用 Event，不复制一份独立事项。 |
| 当前可执行列表 | 此刻有条件执行的主动服务步骤和内部复核步骤 | 由最新 Event、时间、约束及 DailyPlan 临时生成，第一版不单独维护一套状态。 |
| Memory 个性化记忆 | 孩子兴趣、学习习惯、家长关注点、沟通偏好、有依据的观察 | 长期使用，带来源和时间，允许更正；不承担暂停和补课安排的执行责任。 |
| 原始服务档案与学情 | 学员、家庭、服务关系、班期、排课、课节完成、作品、测评等 | 原始数据表为依据，按任务查询，保留数据覆盖时间。 |
| 消息与执行记录 | 收到的消息、回复关联、草稿、发送操作号、回执、实际时间、真人处理记录 | 支持恢复、去重、核验和工作总结。可以引用既有业务系统中的可靠记录。 |
| 当前有效服务约束 | 暂停范围、联系限制、恢复条件、当前负责人等 | 每次判断及发送前读取，不能只依靠检索历史聊天碰巧找到。 |
| 企业知识和服务方法 | 产品、课程、规则、动作、FAQ、案例、系统操作知识、模板与物料 | 解释“应该怎么服务”，不代替特定家庭的当前状态。 |

服务动作可以成为 Skill 的业务依据，但“一行服务动作是否必须等于一个 Skill”尚未冻结。不要仅凭表头含有 Skill 就机械一对一生成文件。主动和被动场景可复用知识与判断方法，但触发入口和执行责任不同。

## 4 Event 的 baseline 建议

以下是供实现讨论使用的推荐结构。已确认的是字段承载的业务含义，字段名、枚举和嵌套位置仍可调整。

| 字段或字段组 | 建议要求 | 含义 |
| --- | --- | --- |
| `id` | 必需 | 稳定事项 ID，跨日不变。 |
| `title` 与 `goal` | 必需 | 这件服务要解决什么，避免只写“发消息”。 |
| `source` 与 `source_refs` | 必需 | 学习信号、固定动作、家长请求、老师请求等来源及原始依据；同一事项可关联多个触发。 |
| `context_refs` | 按需必需 | 学生、家庭、班期、原课节、知识版本、相关消息、作品等引用。 |
| `status` | 必需 | 当前业务进展；不能仅靠此字段决定是否能执行。 |
| `completion_criteria` | 必需 | 怎样才算目标完成，需要什么事实或执行结果。 |
| `next_step` | 有后续工作时必需 | 当前准备推进的具体一步，如核验补课、检查回执、准备图卡；不预先穷举整条流程。 |
| `not_before` 与 `deadline_at` | 按需 | 最早执行时间与截止约束，要明确约束的是事项还是当前步骤；与家庭承诺截止分开。 |
| `wait` | 等待时必需 | 等谁或什么、关联哪次请求、什么新信息可以推动、何时内部复核。 |
| `commitment` | 形成约定时必需 | 原话或消息引用、解析日期与时刻、约定课节、变更记录。 |
| `delivered_parts` 与 `remaining_parts` | 有部分交付时使用 | 已完成什么、还缺什么。第一版可以是简单结果记录，不必建设独立子任务系统。 |
| `owner` 或 `handoff` | 转人工或有明确协作方时必需 | 谁负责下一步、是否接单、实际是否处理、在哪里读取结果。 |
| `result` 与 `history` | 必需 | 实际完成或结束依据、发生时间、未达成原因、重要变更。 |
| `created_at` 与 `updated_at` | 必需 | 创建与最近更新时间。 |

推荐沿用模拟中的六种进展状态，暂不扩充大量枚举：

| 状态 | 业务含义 |
| --- | --- |
| `pending` | 有待推进的工作，可能尚未到执行时间。 |
| `running` | 正在处理当前一步，不代表持续占用执行能力直到整个事项结束。 |
| `waiting` | 正常等待回应、学习结果、真人结果、资料或回执。 |
| `blocked` | 当前推进受到必需资料、能力或其他条件阻碍。仍应检查是否有可独立交付的部分。 |
| `done` | 目标已达成，存在对应依据。 |
| `cancelled` | 已取消、重复归并，或有依据地结束主动跟进；不自动等于服务目标成功。 |

状态名称仍属 baseline 建议。无论最终采用什么名称，都要区分“目标达成”和“没有达成但停止推进”。例如一次非必需互动未收到回答，经判断结束主动追问，要记录未回应，不能计为互动成功。

Event 处于 `waiting` 时，内部复核仍可能已经到时可执行。不要把所有等待统一改回 `pending`，然后再次运行原来的发送步骤。

同一事项第一版保留一个当前下一步即可。只有出现真实的独立分派、并行责任或分别计时需求，再讨论多步骤实体和依赖关系。

## 5 DailyPlan 与当前执行列表

DailyPlan 表达今天打算把哪些事项推进到什么程度，而不是把所有未结束事项完整复制进来。

推荐结构：

| 字段 | 用途 |
| --- | --- |
| `student_id`、`date`、`timezone` | 说明规划属于哪个孩子、哪一天及哪个时区。 |
| `revision` 或变更历史 | 记录重排和计划调整；具体版本实现待定。 |
| `items[].event_id` | 引用原 Event。 |
| `items[].today_target` | 明确今日推进目标，例如“发出互动邀请”或“核实真人是否接单”。 |
| `items[].required_today` | 说明这个阶段目标是否需要今天完成，不要求整个 Event 必须今天结束。 |
| `items[].result` | 今日未推进、部分达成、达成或已无需执行，以及时间和证据。 |
| `activity` 或等价记录 | 今天实际做过的查询、判断、发送、复核与等待决定。 |

`items` 的顺序可以表达建议优先顺序，暂不需要复杂的分值算法。重排只改变尚需推进的安排，不能把已有达成记录重置成待办。

当前执行列表按下面的顺序判断：

1. 先检查是否有尚需处理的家长或孩子来信，有则先走即时响应。
2. 查找相关事项是否存在此刻可做的具体下一步。
3. 核对时间、必要数据、有效约定、暂停范围、同家庭近期沟通和操作结果。
4. 在可执行工作之间排序，选择一次推进的步骤。
5. 做完这一步，写回结果并重新判断；不要求一直执行到整个事项结束。

展示上采用三个视角：

- **现在可做**：只有这一组有当前执行序号。
- **等待与约定**：保留等待对象、恢复条件和复核时刻，不占执行位置。
- **今日已处理**：记录今天实际做过什么；允许今日目标达成而事项尚未结束。

三个视角不要求三个互斥的数据副本。同一 Event 可以出现在“等待与约定”里，同时在“今日已处理”中留下已经发出邀请的记录。

当前没有可执行工作时，可以空闲等待新信息或下一个复核节点，不必为了填满队列而新增联系。

## 6 即时回复与后续事项的衔接

回复不属于主动服务规划。收到提问或需要回应的孩子表达，先理解并回应；不需要先匹配到某个 Event 才获得回复机会。

一条来信可能影响多个事项。例如“第3节明早补，先别催，过去的课从哪进”同时包含补课变更、联系约束和操作问题。即时回答入口问题，同时把约定与暂停写回相应记录。

需要保留以下区别：

- 家长问了另一个问题，不代表已经回答原互动邀请。
- 孩子发来与原邀请有关的表达，应即时点评，并更新原互动事项。
- 即时回复中如果承诺后续核实、准备资料或安排真人，需要留下后续履约事项；不能因为“回复不进规划”就漏掉这些责任。
- 家长连续发来的多条消息要共同保留。回复完成只结束实际覆盖的那些来信，后来到的或尚未覆盖的消息继续优先处理。
- 回到主动工作前重读相关状态，不直接执行被打断前的旧草稿。

记录已处理消息与回复的关联，比只维护一个“对方有没有回复”的布尔值更可靠。第一版至少能回答“哪条来信还没处理”“这条回应覆盖了哪些消息”“满足了哪个等待条件”。

## 7 等待与结束规则

| 等待对象 | 需要保留的内容 | 复核或新信息到来时做什么 |
| --- | --- | --- |
| 孩子或家长回应 | 原请求或邀请、预期回应内容、回应必要性、复核安排 | 判断是否有相关回应，是否还值得跟进；回复走即时通道。 |
| 补课等学习行为 | 原课节、家庭约定、最新学情及数据覆盖时间 | 先查询真实学习结果，不要求家长额外回一句“完成了”才能结案。 |
| 发送回执 | 原操作号、已发起事实、当前结果、查询方式 | 核实同一次发送，不能因为复核到点就重新发送。 |
| 真人处理 | 请求、负责人、接单情况、约定时间、实际处理结果 | 区分已转交、已接单、已完成。 |
| 必需资料 | 缺什么、谁负责补齐、当前已交付部分、下一次检查 | 判断是否能推进已有部分；资料补齐后继续原事项。 |

回复必要性可以区分“必须回复、最好回复、可以回复、不需要回复”。这是判断等待和后续工作的依据，不是自动生成催促的开关；具体字段枚举尚未冻结。

对方没有回应时，原因可以保持未知。没有依据时，不能强行归类为没看到、没来得及或不愿回复。

非必需互动不应无限积累。经过判断，可以结束本次主动跟进并记录未回应。何时结束仍需结合约定、服务价值、近期接触和适用规则，不能把模拟中的间隔写成公司制度。

必须取得的确认或老师已经承诺的服务，不能仅因沉默就自行结束，应继续处理、明确取消或转真人承担。

停止追问以后，孩子迟来回答仍应被立即接住，并关联原邀请。是否重新打开原 Event 是实现选择，但要保留历史，不能把先前未回应改写成当时已经完成。

## 8 时间与有效约束

用户明确要求时间精确到几月几日几点几分。人读展示可使用“10月17日 10:10”；存储建议使用包含年份和时区的绝对时间，例如 `2026-10-17T10:10:00+08:00`。

以下时间必须分清，不能共用一个含义不明的截止字段：

| 时间 | 示例与含义 |
| --- | --- |
| 消息发生时间 | 家长在10月16日20:40提出变更。 |
| 家庭约定截止 | 家长约定10月17日10:00前补完 D3。 |
| 最早执行时间 | 某个主动步骤在指定时间前不启动。 |
| 内部复核时间 | 10月17日10:10查询是否完成，不等于此时必须联系。 |
| 老师的服务截止 | 已明确承诺何时提供资料或完成处理，责任主体是老师。 |
| 数据覆盖或同步时间 | 10:10查询到的结果可能只覆盖09:30，不能据此认定10:00的约定未兑现。 |
| 操作发生和确认时间 | 10月18日20:25发起并实际送出的图卡，可能到10月19日09:01才确认成功。 |

相对时间按消息发生时的日期与时区解析，并保留原话。家长说“明天白天”，可以确定日期，不能自行补成10:00；内部另定复核时刻时，要标明它是内部安排。

如果复核时刻同时用于等待记录和步骤调度，后端应选择一个权威来源，另一处派生，避免两处独立维护而不一致。

暂停要求需要维护作用范围、生效时间、明确的结束条件或恢复条件以及来源。没有给出恢复时刻时，不自行添加“几天后自动解除”。暂停催课不自动禁止回应新问题，也不自动意味着其他主动联系一定合适。

模拟用 E06 表示约束记录并排除出计划。这是演示组织方式，不代表生产系统必须把所有约束做成 Event。底线是它能被可靠查询和更新，发送前会实际生效。

## 9 个性化记忆

个性化记忆与历史沟通、结构化学情、企业知识共同参与服务。用户特别强调记忆的重要性，当前只从正常服务中逐步积累。

| 类别 | 可以维护的内容 | 使用边界 |
| --- | --- | --- |
| 孩子兴趣与偏好 | 喜欢小动物、小猫，愿意画画，喜欢的表达主题 | 合适时用于例子、沟通和报告主题，不强行套进所有内容。 |
| 学习习惯与条件 | 经常的学习时段、需要的支持方式、稳定出现的学习安排 | 区分稳定习惯与一次临时安排；没有依据不补全画像。 |
| 家长关注点 | 关心理解、表达、兴趣、坚持等具体问题 | 围绕已知关注点反馈，不反复要求家长重新说明。 |
| 家长沟通偏好 | 建议简短、一次说一件事、喜欢某种沟通方式 | 来自明确表达或可核查观察，允许后续更正。 |
| 学习观察与有效经验 | 某次表达能用故事细节支持判断；某次建议之后出现了什么结果 | 一次表现不升级成长期能力定论；不能把同时发生写成已证实因果。 |

每条记忆至少建议保留：ID、对象、内容、依据类型、来源引用、观察或陈述时间、当前是否有效，以及修改时间。依据类型要区分孩子明确表达、家长转述、老师观察和暂时推断。

“孩子明确说喜欢小猫”可以立即用于适合的解释和图卡主题；不能同时记成“动物主题已经显著提高学习兴趣”。后者需要额外效果证据。

补课约定、暂停要求、未完成服务、发送结果和当前负责人属于可执行的业务状态，不能只塞进长期记忆。家庭经验进入公共案例或共享知识前，需去标识并经维护审核。

## 10 原始数据与执行记录

学生基本档案、班期、排课、完课、作品和测评，优先读取现有数据表。不要为了建立 Memory 再复制一套相互竞争的学情事实。

检索课程时要关联原课节、级别、班期与课程版本；课程内容版本和书籍出版版本分别维护。周五补 D2，仍使用 D2 的课程资料。

发送与执行至少需要能查到：

- 原操作标识、关联事项和目标消息或素材。
- 草稿、已提交、结果未知、已确认成功等阶段。
- 实际发起时间、返回结果、确认时间和回执引用。
- 操作失败或不确定时下一步如何查询、重试或转人工。

未发出的旧草稿可以因新信息而失效。已经提交的发送不能假装撤回；结果未知不等于确定失败。跨日重建 DailyPlan 时，不清除待处理来信、未核实的发送或对应责任。

工具清单和权限来自可信应用配置。聊天里自称管理员的文字不能修改执行权限。缺少真实接口时，只交付当前能完成的草稿、资料或内部判断，不能声称已经查询、发送或保存成功。

## 11 服务判断与沟通风格

同一家庭的多个事项都满足各自条件，也不等于应连续发送多条消息。主动联系前，应结合正在讨论的话题、最新情绪与安排、近期触达和内容是否适合合并，重新判断。

对外表达需要接近日常老师微信沟通：简短、具体、回应眼前的问题；减少流程复述、机械共情、空泛表扬、固定收尾和不必要的反问。系统内部的状态、判断术语和记录过程不需要讲给家庭听。

自然表达不依赖虚构个人经历、真人身份或已经执行的操作。没有真实接单结果时，只能说明正在协调，不能提前承诺电话已经安排好。

可参考第二版的表达：

> 好，那先不催。阅读课页面上方有一排小书本，点第1、2、3节，就能找到前面的课。

> 对，爸爸手机也下个少年得到，登您买课的账号就行。普通课程不影响，直播别两台同时开就好。

孩子的反馈要点出本次具体表达，同时控制建议数量。只有完课记录时可以鼓励参与；需要评价理解、复述、写作变化或方法迁移时，必须有相应证据与比较范围。

## 12 最新模拟及验证边界

最新版本为第二版，共38步，使用虚构的单个孩子“小宇”、2026年10月16日至10月19日的情境。案例日期用于演练，不代表真实发生的服务。

第二版覆盖：

- 相同缺课信号关联原事项，不重复创建工作。
- 草稿生成后收到家长消息，旧草稿失效，先即时回复。
- 补课约定变更、旧复核失效、明确范围的暂停与恢复。
- 邀请发出后退出当前执行列表，今日目标达成但互动继续等待。
- 孩子新问题不冒充原互动的回答。
- 学情同步延迟，内部复核继续等数据，不直接认定失约。
- 家长明确要求先不追问，结束本次主动跟进；迟到表达仍被即时回应。
- 有表达素材后才生成高光卡工作。
- 周总结先交付已知部分，缺失课表保留后续责任。
- 连续两条来信共同保留，一次回答明确关联两条消息。
- 发送结果未知跨日保留原操作，查询成功后不重复发送。
- 真人请求、接单和实际完成分别记录。

已保存的验证结果：38步、18项脚本一致性检查通过；浏览器检查覆盖全部步骤、日期显示、数据选择、分页切换、播放暂停、前后切换及1100、360、320像素宽度，未记录页面脚本错误。

这些结果验证的是演练脚本和有限的可执行条件，不代表任意输入下的自动规划、真实模型判断、外部接口、媒体生成、多学生并发或持久化恢复已经通过测试。情节和决策仍由脚本提供。

## 14 接手后的工作建议

先读本交接，再对照动作表和第二版模拟，保留用户已经确认的边界，不回到“所有未完成事项排成一列，等第一个结束才做下一个”的模型。

下一轮业务验证优先增加：没有家长明确停止要求时的长期未回应、必须确认的信息持续缺失、回答过程中又来新问题、同一事项部分可做而部分等待、多个主动事项同时适合联系、进程重启后的未知发送恢复。

进入后端设计前，先确认当前可用的数据表、工具、身份与权限、时间规则和最小触发配置，再把本文的推荐字段收敛成实际契约。不要用不存在的工具或模型自行补出的规则，把设计演练包装成真实业务闭环。
