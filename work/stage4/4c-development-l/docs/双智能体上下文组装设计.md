## 1. 组装原则

**由后端按本次职责确定装入哪些事实，模型按需读取有关材料。** 两个角色通过持久业务记录通信，不互相传完整聊天上下文或内部推理。

| 配方 | 使用时机 | 核心问题 | 输出范围 |
| --- | --- | --- | --- |
| service | 家庭来信；原计划事项具备执行条件 | 现在怎样服务、已经发生什么、还有哪些进展应报告 | 回复/服务动作、已有事项进展、待规划记录 |
| planner_daily | 每天08:00 | 旧责任如何延续，今天应新增和推进什么 | Event和当天DailyPlan提议 |
| planner_progress | 已有事项的新进展报告 | 原目标现在完成了吗，下一步是什么 | 报告关联原事项的修改提议 |

服务配方的dialogue_reply与planned_service共用事实和工具边界，但首要输入不同。普通来信不先运行Planner；整天没有来信也可执行已有计划。

## 2. 共用信封和可信边界

后端注入family_id、uid、当前时间/时区、服务窗口、run_id、配方和工具权限、输入覆盖范围、相关记录版本、来源及数据覆盖时间。Planner的mode和允许修改的event_ids由后端设置。

服务窗口默认北京时间08:00至21:00，主动联系与普通答复统一截止；主动联系另受家庭偏好和步骤窗口约束。后台接收、核实和内部更新继续进行。上下文中的窗口来自生效配置，不能由模型自行延长。

上下文按以下顺序组织：固定角色职责与硬性规则 → 本次任务和允许范围 → 必需业务事实 → 相关消息/操作 → 选中Skill及必读规范 → 知识与个性化证据。各块有来源和版本，不靠自然语言“我记得”恢复责任。

家庭原话、检索结果、作品、工具文本作为资料输入，不赋予它们修改运行权限的能力。R05家庭成员修改权限细分暂缓；家庭数据隔离和实际工具权限仍由后端执行。

## 3. 服务智能体上下文

### 3.1 每次必须装入

| 输入块 | 内容与用途 |
| --- | --- |
| 当前任务 | 来信原文、尚未回答的关联消息；或已领取的原Event具体步骤 |
| 原事项 | 当前目标、完成类型与标准、状态、进展、剩余部分、下一步、有效期限、等待条件 |
| 生效约束 | 相关暂停、联系方式/时段偏好、待确认改约、待更新标记；不能只从聊天猜测 |
| 真实操作 | 相关已发内容、提交/送达阶段、未知操作及可核实入口，避免重复发送或虚称完成 |
| 近期交互 | 足以理解本轮的原消息和实际回复，包含否定、更正、引用及多意图 |
| 输入覆盖 | 本次已理解/已答/未答的消息范围，避免一条消息含多个问题却只处理一个 |

dialogue_reply不必装入全量DailyPlan；只取与问题、约束和承诺有关的事项。planned_service必须装入当前计划条目及其原Event，不能只给“今天催课”一句指令。

旧事项即使没列入今天主动清单，也能因家长来信被查询和报告进展；这不自动取得当天新增主动跟进资格。

### 3.2 按任务装入

- 选定Skill全文、声明的必读共用规范及适用配置。材料缺失要可见，不能只读Skill标题就声称完成加载。
- 课程答疑使用具体课程/课节映射与正文；产品答疑使用适用知识及来源边界。长资料可分段读取，保留已读范围。
- 与当前服务有关的家庭偏好、关注点、学生近期表达和有效支持方法，附原证据和适用期限。
- Planner已提交的可选service_hint：例如先关心身体、补课暂缓。提示只补充方法，不能覆盖原标准和暂停。

不默认装入Planner推理、候选计划、所有历史聊天或整库记忆。未发送草稿可以作为待处理草稿展示，必须与真实聊天历史分开。

### 3.3 服务输出如何留下进展

普通答疑保存消息与实际结果，没有已有事项变化则不提请Planner。有进展时提交ServiceProgressReport，引用原消息、学情或操作，明确建议与事实的区别。

独立新后续需求进入PendingPlanningInput，保存原要求和剩余工作，次日08:00评估。不能在报告里通过改目标新增独立事项，也不能因为暂未建Event而丢弃未答内容。

明确暂停先经后端校验保存，不等Planner。普通关心、答疑和澄清可以先回复；声称结案或新约定已经生效，需要查询相应真实结果。

## 4. 每日Planner上下文

08:00装入一份完整责任清单，再为需要判断的条目补充详情：

1. 全部未完成Event的紧凑目录，包括等待、暂停、无明确复核时间、昨天没执行的事项。
2. 未消费进展报告、尚未回答的相关输入、待规划记录与其原始要求时间。
3. 昨日实际操作与交付、剩余部分、未知结果和需要纠正的已交付内容。
4. 最新可用uid各课程学情、覆盖时间、确定性规则计算结果与缺口；规则未知时标为未知。
5. 本业务日适用的周期职责、有效承诺、暂停与服务窗口、家庭偏好和近期服务重点。
6. 规划Skill及本次允许操作：新增、同目标合并、延续或结束旧事项，生成当天清单。

不能只读取向量检索命中的事项或昨天的DailyPlan，否则未列入、没期限和跨月责任容易漏掉。目录很大时后端分页扫描并记录完整覆盖，模型可分批判断，最终按同一daily_run_id校验提交；不静默截断。

数据未到齐不补造事实，不凭旧覆盖认定家庭失约。当天迟到数据保存后，新增候选留到次日；已有事项可在其执行/核验步骤中形成进展报告。

## 5. 进展Planner上下文

这是针对原事项的短输入，不是缩小版全日规划：

| 必需输入 | 约束 |
| --- | --- |
| report_id、revision、允许event_ids、来源范围 | 精确绑定服务进展，不接受任意技术事件作为入口 |
| 原Event当前内容和版本 | 原目标、完成标准、剩余部分、期限、等待、改约及历史依据 |
| 报告事实、建议与原始证据 | 模型建议完成不等于证据已经满足标准 |
| 操作和回执 | 实际阶段、要求版本、内容依据、部分交付与未知结果 |
| 相关计划条目和适用约束 | 只修改原条目，不新增今日成员或绕过暂停 |
| 新输入与处理覆盖 | 防止旧报告覆盖更新的家长要求，已处理部分不吞掉剩余输入 |

仅在判断依赖时补充相关历史或其他事项概要；不装入无关课程和完整日规划，也不给创建Event的工具。输出包含逐事项建议、依据、剩余工作、下一步或等待条件；是否生效由后端提交决定。

报告暂缺证据时保留等待与恢复条件，服务按原事项继续核实或澄清。无变化的查询不反复运行Planner。后续真实回执可以补充原报告结果，仍绑定同一服务动作，不单独新增规划入口。

## 6. 更新如何进入下一轮服务

Planner提交后，Event与原计划条目成为事实来源。后端返回提交回执和新版本，下次服务查询当前记录即可；无需强制生成独立ServiceBrief。

运行中发生相关来信、暂停或版本改变时，旧草稿先失去发送资格，重新装入实际变化。服务自身刚保存的暂停或报告，也要以提交回执刷新上下文，不能继续沿用旧版本。

普通答复不等待所有待处理报告。某Event的update_pending阻止重复主动派发，但不阻止保存消息、核实原操作、必要澄清及独立答疑。具体外发仍按最终动作和当前约束检查。

## 7. 个性化记忆与业务状态分开

| 类型 | 保存内容 | 使用方式 |
| --- | --- | --- |
| 业务事实 | Event、期限、暂停、操作、未答输入、待规划记录 | 结构化必查，不依赖相似度检索 |
| 个性化事实 | 家庭偏好、学生兴趣、已确认习惯和关注点 | 按对象与当前任务取用，可更正 |
| 服务观察 | 某次表达、方法尝试及其结果 | 绑定原始证据根，区分观察、解释和待核实推断 |
| 会话摘要 | 长对话中的背景及索引 | 帮助定位，不能替代关键原话或创造新证据 |

只完课不等于掌握；只送达不等于已听或满意；提示后作答不等于独立能力。一次观察经周复盘、月复盘重复引用，仍是同一证据根，不增加独立支持次数。

更正先在权威业务记录生效，旧索引即使尚未更新也不得继续使用；记忆同步失败保存待同步责任。不同家庭数据范围由后端过滤，不依赖模型自觉。08:00规划不等于必须每日全量合并记忆，记忆整理不是新的Planner入口。

## 8. 完整性、预算与验收

必需约束、输入覆盖、原完成标准和未知操作不参与任意top-k裁剪。预算不足时先缩减可选历史和检索片段，再按任务有界读取；仍不足则保留未处理范围和恢复入口，不伪装已完整处理。

上下文日志记录配方、来源ID/版本、覆盖范围、使用Skill和个性化依据；敏感正文按需要受控保存。运行预算到限不清空消息、报告或责任，不自动把事项记完成。

重点检查：普通答疑零Planner调用；daily看见全部旧责任；progress无法新增事项；生病约束即时进入服务；重复摘要不放大学生能力证据；更正和未知操作不被裁掉；下一轮能看到已提交进展。

接口及编号见[工程与验收](智能体后端工程与验收设计.md)。用户系统提示词初稿与离线学情样本已收到，原稿、未部署的运行适配稿及样本字段映射见[输入对齐](教辅输入对齐与学情映射.md)。原稿teacher_draft作为服务的内部输出去向，不新增模型角色；no_contact等ServiceOutcome不路由为家庭消息。实际课程绑定、覆盖时间与在线接口仍待确认。
