## 已发现并交主控修复

1. **未消费 progress 被误标成功**：`Worker.run_once` 起初只对 daily/service 检查实际结果，progress handler 空字典正常返回会把工作标 succeeded，报告仍 `resolution=None`，Event 仍 `update_pending=True`。该工作不再可领取，后续 daily 被 `REPORTS_PENDING` 阻断。新增 `test_progress_empty_return_cannot_abandon_unconsumed_report`。
2. **空步骤被误标成功**：step handler 无核验结果、操作或进展报告时同样正常结案，使原步骤当日不再有恢复执行入口。新增 `test_empty_step_return_preserves_schedulable_responsibility`，同时检查无变化扫描不重复调用模型。应明确“有依据不行动”与“运行正常返回但未完成责任”的区别。
3. **暂停未退出原步骤队列**：Control 已暂停催课，但 Planner 尚未更新 Event 时，Scheduler/Worker 起初仍派发 remind_makeup 步骤；发送层会阻止外发，却仍占用执行及调用模型。S05 要求无需等待 Planner 即退出催课执行。新增 `test_s05_pause_blocks_step_even_without_planner_update`，正常入口答复仍必须成功。

以上是代码可修复问题，已即时通知主控；未发现需要改动 Hermes 核心或改变已确认业务规则才可继续的架构阻碍。修复完成前不应宣称第二阶段通过。

## 独立新增场景

测试文件包含 8 项：

- 普通问题在没有当日计划时完成模拟答复；调用序列仅 service，无 daily 提交。
- 空 progress 正常返回仍保留报告处理责任。
- 空 step 正常返回仍保留步骤责任；无变化扫描不再调用模型。
- 暂停后即使 Event 仍 pending，也不再派发催课步骤；普通问题正常答复。
- 内部 review 对事项外发与普通答复两条路径都返回 `NO_CONTACT_RUN`。
- 无 review_at 的等待事项跨两日、两次重启仍保留原 ID、期限及剩余工作，无外发。
- 原操作 unknown 跨日复用同 ID、不再发送；迟到 sent 回执只生成一条外发记录，提醒不完成学习目标。
- 新服务报告在次日 daily 快照后到达时，旧提交被拒绝；报告和待更新标记保留。

## 修复后二次源码复核

主控修复后再次独立阅读 `scheduler.py`、`jobs.py`、`outbox.py` 及 `simulation.py`，结论如下：

- progress 收尾检查报告 resolution，未消费保持 waiting；step 未产生新进展且目标未结束保持 waiting，空返回不再丢失执行责任。
- Scheduler 入队前与 Worker 调用处理器前均检查匹配动作的 Control。旧队列中的催课保留 waiting，正常答复与内部复核继续按各自权限执行。
- review 除工具硬性禁止外发外，正常完成还要求显式内部 `no_contact` 结果；没有该结果则保持 waiting。
- `reconcile` 在原操作结果没有变化时不再更新家庭版本；得到新回执才变更版本，原 waiting 步骤可被重新领取。不会把每次无变化查询变成一次重新调用模型的理由。
- 两日模拟通过原 `step` 处理器查询同一 operation，将确认后的操作版本作为原 Event 的服务报告证据，再由 progress 正式提交完成。脚本不是直接改写数据库状态伪装恢复。
- 模拟在第二部分交付外部已执行、业务尚未保存时注入 `InjectedCrash`，重启后比较渠道操作计数；同时检查次日晚间来信只新增一次答复、等待原事项未结案、待规划原期限保留和空扫描零处理器调用。

三项已报告缺陷在源码层闭环，新增8项测试与修复后的公开行为合同一致。未发现新的需用户裁决的重大阻碍。服务器全量测试及模拟结果仍由主控正在执行；获得对应产物后才能将“源码复核通过”升级为“程序验收通过”。
