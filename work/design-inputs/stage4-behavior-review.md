## 2. 三条首批主线

### A. 课程答疑：入站直接服务

可信绑定课程/版本/课节，读取必要原文，回应家长实际困惑；可以选择一个小示例或引导。普通问题无需先 Planner、无需为了闭环创建 Event。模型自行识别意图、选择 Skill/资料、组织说明、判断缺口；程序限定家庭、课程范围、实际工具和最终发送资格。

必须包含四个分支：资料充分直接答；课程绑定未知只问关键缺口；目标课缺失而相邻课有材料时不冒充；暂停催课的家庭提出新问题时正常答疑但不恢复催课。

`explain-lesson` 对给孩子的讲解有语音要求。文字能力可以交付家长文字解释和可朗读稿，必须标记语音未交付。首批“全部完成”正例可限定家长自己的课程事实问题，不用儿童语音需求做文字成功替身。

### B. 目标型补课：沿原课节维护实际学习责任

daily 基于已确认规则候选或此前家长请求决定是否形成目标，保存原课节范围与 goal 完成标准。服务自主决定联系、等待或核实，发现生病暂停立即落 Control；暂停不等于 goal 完成。提醒发送、家长理解入口、家长承诺与实际完课分别记录。

每次新消息，模型先从当前未结事项索引中选择可能相关项，再读取详情与原证据；选择关联只是提议，程序校验 ID、版本及同家庭范围。当前未列入 DailyPlan 的旧事项可以更新进展，不能由关联自动获得当天主动发送资格。

至少包含两课目标只完成一课、暂停后新问入口、晚到旧消息、约定未到、数据覆盖未知、权威完课更新六个分支。未确认连续缺课阈值时，首批使用明确补课请求作为候选来源，或仅用带 simulation 标记的规则，不为演示自行启用生产阈值。

### C. 交付型反馈：按原约定内容逐部分完成

首批文字正例必须有明确的文字反馈请求，例如“给我本周参与情况和一个建议，用文字即可”。daily 冻结本次范围、采用的 Skill/规则版本、必要部分及 required_stage。两个 part 应对应两个真实交付义务，例如参与事实回顾与可执行建议；同一条消息重复登记两个 part 不能算两次独立交付。

模型负责选用有依据的事实、描述作品当次表现与组织建议；程序负责原要求版本、准确对象、part 范围、操作去重和回执。参与次数不证明能力提升，单次回答不证明长期进步。

`review-learning-progress` 的月度服务要求图文报告。若测试的是月度图文，应保持图卡这一必要 part，工具缺失时正文可先交付但整体等待；不能在执行中删掉图卡或临时改成文字后宣称全部完成。语音同理。若为明确局部文字请求，则从建立时就按该请求定义文字范围，不冒称完成月度图文服务。

part 的内容不应只有任意字符串 ID：建议声明媒体类型、简短交付目标、必需材料及要求版本。代码判定 delivered 只证明该对象/部分的操作阶段；是否真正答到要求，需要独立语义验收，不能用“body 非空”替代。

业务设计相关的七个入口为：`plan-proactive-service`、`close-service-case`、`explain-lesson`、`answer-course-service-question`、`plan-makeup-learning`、`review-learning-progress`、`follow-up-unanswered-question`。交叉评审后建议本阶段冻结主控已列的五个正式方法接入范围，另两个作后续候选，不据此扩大材料授权或验收承诺。

| Skill | 本阶段方法范围 | 当前真实API材料范围 |
| --- | --- | --- |

S链只能使用明确合成的任务规则和夹具，不把未批准原Skill换文件名后传出。S链通过不把对应正式Skill标成真实材料语义通过；正式必需分支未验证时列出该范围，不整体宣称完整通过。

- `plan-proactive-service` 正文目前仍谈时间/条件多入口，应明确 daily/progress 两配方、原目标及今日成员约束；不能只靠 loader 末尾追加约束长期覆盖旧正文。
- `close-service-case` 目前谈关闭子任务、写回原事项，应明确服务只汇报事实及未完成范围，正式 Event 完成由 progress 提议和后端核验。
- `prompt-backlog-makeup` 仅在“当日新课已完、往期仍缺课”条件具备时追加；不作所有补课的默认入口。
- `weekly-learning-review` 暂不纳入首批必需集，因为它另依赖周课表、下周预告及分层；后续扩展单独验收。
- service-basics的有效底线可并入每轮固定基线，并记录全文版本和覆盖，不强迫简单事实答疑再调用一次读取工具；模型选择的业务 Skill 仍必须连同声明的 guides 完整加载。不要为了强制调用 Skill 把简单事实答疑变成完整访谈。
- Skill 引用的 `agent/config/service.yaml` 有 pending_confirmation 字段。应提供“本次生效配置”投影，保留未确认状态，避免模型把文件里的候选数字当成授权规则。

服务运行基线应使用已有完整运行适配稿，保留用户正文与示例，但逐段清点示例、工具名称、输出协议与实际实现是否一致。Planner 使用独立精简合同，包含证据、完成标准、daily/progress 权限与业务约束，不把全部家长沟通风格和教学模板硬塞给 Planner。

每轮记录：系统运行稿版本与 hash、配方版本、选中 Skill 与全部必读指南 hash、实际读到的知识正文 hash、绑定版本及覆盖状态。压缩优先处理可选历史，不静默截断硬性规则或原完成标准。

## 4. 程序固定与模型判断的边界

| 程序固定并校验 | 交给模型判断 |
| --- | --- |
| family/uid/渠道身份、角色与输出模式 | 当前问题含哪些意图，各自需要回应或后续处理 |
| 时钟、服务窗口、有效 Control、租约与撤销 | 现在联系能解决什么，是否保持等待 |
| 原课节/课程映射、来源版本、日期精度 | 在允许范围选择哪个知识和 Skill、怎样解释 |
| 确定性统计、缺失/unknown、数据覆盖 | 事实可能说明什么、哪些结论证据还不足 |
| 候选业务键与允许范围、正式 Event 的建立入口 | daily 采用/保留哪个候选、今日次序和服务方法 |
| 原完成标准、required parts、提交原子性和进展范围 | 根据证据建议继续、等待、部分完成或完成 |
| 操作身份、回执单调合并、未知查原操作 | 具体文案与适合当前家庭的一项下一步建议 |
| 权威证据生成规则、修订及失效传播 | 解释家长原话，提出待验证的改约/取消建议 |

两个风险不能靠提示词掩盖：当前 goal_key 可由模型自由写，同义目标可能换键重建；建议由候选/原课节集合的可信业务身份提供去重键，模型决定采用，不决定身份。当前文本 action_kind 由模型声明，reply 文案可能夹带催课；需要内容级语义验收及受限动作建模，不能把“标签为 reply”当成内容合规。

## 5. 最小可信证据桥梁

当前 `planning.py:7` 的 goal 完成依赖 trusted lesson_completed；改约接受、取消和重开依赖 trusted evidence（`:41`、`:54` 等）。`application.py:230` 的 add_evidence 是宿主入口。第四阶段不得继续由验收脚本在关键步骤预先注入“正确答案”。

建议按证据类型拆小桥梁，模型只提出候选与来源，不传 trusted=true：

1. **学情证据**：受控核验工具读取当前家庭已绑定的源批次、具体 lesson 映射、源状态及覆盖/适用性，程序生成 lesson_completed 引用。模型说“查到完课了”或传入任意 SQL 结果文本不能成为证据。负面未完成断言尤其要检查覆盖时间；未知不创建失约结论。
2. **暂停**：沿用 control.apply 的低影响立即停止路径；原因/范围保留原文与消息版本。解除暂停比新增暂停更严格，不能将一次普通答疑或旧消息当恢复许可。
3. **接受已有改约**：模型提交 source_message_id/version、现有 change_id、引用片段及解释；宿主核对同家庭、原提议仍有效、提议原内容未变、对应确认问题实际已发送、回复发生在提议后，且消息确实明确指向它。当前 Inbound 只有 external_id/body/occurred_at，没有可信回复关联，不能仅凭模型补出关联。
4. **最小明确同意范围**：可在 mock 渠道加入真实的引用消息/确认动作结构，再支持“对已绑定确认问题的纯明确肯定”这类窄范围；不能用任意文本含“好/可以”判断同意。未引用、同时多个待确认、混合否定或附加条件的自然语言继续 needs_input，模型可发明确确认问题。模型猜出完整时间之后让宿主照单盖章不成立。
5. **日期精度**：“周五补”只保留日期精度和原话，内部 review_at 由独立配置产生；现有 proposed_due_at 是精确 ISO 时间，不应用午夜/23:59 强行代替未知时刻。首批正式改约正例可限定已有精确提议的明确接受；日期级约定应先补 precision 合同或只作为待明确安排保存。
6. **取消与更正**：“别催了”默认停止对应触达，不等于取消学习目标、更不等于完课。明确取消原跟进的确认，可使用同类关联确认桥梁；已完成事项重开则由权威源修订/人工确认产生 correction，不开放模型自证更正。更正影响范围按原证据关联传播，不清空所有事项。

最小首批可覆盖：可信学情完课、立即暂停、明确指向既有精确改约提议的同意。广义自然语言取消、多条件改约、无精度期限、任意已完成重开可保留明确未覆盖并等待澄清，不伪装自治已跑通。

## 6. 4A—4E 可验收拆分

| 子阶段 | 具体交付 | 验收不能替代的事实 |
| --- | --- | --- |
| 4A 合同与运行装配 | 全量服务基线、Planner 两配方、Skill V1正文、可信任务信封、当前事项索引、输出结果与证据桥梁合同 | 通过正常 Worker 路径可观测实际加载版本；材料/任务不靠 probe 的临时 system/prompt 开关 |
| 4B1 纯被动问答链路 | 微信入站→自主查询知识/SQL→真实模型→模拟回复→回执/未答 | 不在 prompt 指定工具序列或答案；宿主passive只允许绑定入站reply_to的回复；禁daily/主动step/定时触达；先验链路再扩行为 |
| 4B2 被动服务行为 | 多意图、暂停与答疑、草稿、既有事项索引、报告持久化 | 不执行progress；原报告保留；暂停仍生效；普通答疑Planner调用数为0；旧daily/step/review任务不能因环境残留绕过passive |
| 4C 每日规划 | 程序事实/候选→Planner选择→一次性提交 | 从源事实和请求形成目标，不预填event字段答案；全部旧责任有去向；重复醒来不重复建事项；未确认阈值不生效 |
| 4D 执行/进展/恢复 | 原计划服务→报告→绑定progress→原事项更新；学情与明确确认桥梁 | 不手工submit_report/add_evidence补出本应模型/适配器产生的中间步骤；部分交付、未知操作、过期草稿和更正均保留真实结果 |
| 4E 两日综合 | 同一冻结版本、持久数据库、虚拟时钟、普通队列和真实模型运行 | 多意图入站、暂停与答疑并行、goal与delivery分离、跨夜未答、次日恢复；空闲无模型、故障不重复触达；原运行证据可追溯 |

被动门禁必须进入可信会话和最终发送检查，同时限制任务领取；仅不启动Scheduler不足以挡住旧任务、手动误唤醒或模型外发请求。4A的三配方仅在隔离状态中作装配冒烟，不提前启用正式主动循环。4B1通过后扩展4B2，4B2通过后才进入4C。

**4C与4D依赖取舍：** 保持既定顺序，不为演示绕过 `commit_daily` 的未消费报告门禁。4C用无待消费report的独立家庭验证自主daily；有report的分支只验daily被阻止而来信仍可服务。4A最小progress证明接口装配，不冒充复杂语义已通过。4B2留下的真实报告、未答与事项原样保留，4D用其原始快照验收progress消费后daily恢复，4E再验并发和跨日。4C通过不代表已有被动环境可直接整体切主动；综合切换需4D闭环通过。这样不存在“先通过完整progress才能测任何daily”的循环，也不会靠手工清空报告制造通过。

测试脚本允许注入家庭来信、源学习记录、模拟时钟及渠道超时/回执；禁止在评分前偷偷指定模型选择哪个 Event、写哪个状态、调用哪些工具或代它补齐报告。可有独立“工具协议冒烟”继续保留，但不要计入自治语义通过率。

每个场景至少保留一次反事实分支（例如同样缺课但有效暂停、同样回复“可以”但没有明确引用、只改相邻课资料），确认结果随事实变化而非背固定剧本。语义评分由未参与生成的智能体核对事实/出处/未完成范围，再由结构断言核对状态及操作；评分意见不能写回业务数据库。关键条件任何一次失败都保存失败轨迹并修复重测，不能只择优保存成功轮次。

## 7. 需要明确的争议点

1. “全量运行稿”应接入服务正文，不等于每轮全量课程/全部 Skill/全家庭历史。固定行为基线与按需事实要区分。
2. 当前 no_contact 是宿主根据 review 入口派生，不是完整 ServiceOutcome。应由受控内部结果保存明确结论，并以实际操作状态校验；最终自然语言永远不是发送事实。
3. 文字反馈能够作为明确局部请求的完整交付；不能把月度图文或儿童语音要求消失掉。首批定义从建立时固定，能力缺口保留剩余 part。
