## 2. 最小数据结构

以下是逻辑记录，可按实现合并表，不要求每个对象单独一个服务。

| 记录 | 必需字段或内容 | 不变量 |
| --- | --- | --- |
| ServiceEvent | event_id、family_id/uid、稳定目标、completion_kind/rule、status、progress、remaining_work、next_action、waiting、due_at、proposed_change、delivery_parts、evidence_refs、version、update_pending | 原目标/完成标准不能在白天被降低或替换为新目标；跨日沿用ID |
| DailyPlan | family_id、business_date、timezone、daily_run_id、revision、原Event条目、今日目标/顺序/窗口、实际结果 | 08:00提交后当天成员范围固定；progress只更新原条目，不整体重排 |
| ServiceProgressReport | report_id、revision、event_ids、source_refs、progress_facts、suggested_update、remaining_work、operation_refs、input_coverage、处理状态和回执 | 引用已有事项；事实和建议分开；精确版本幂等 |
| PendingPlanningInput | input_id、来源、提出时间、内容、原要求时间、已做/未做部分、消费结果及关联Event | 白天不进入正式主动清单；次日daily不能漏掉 |
| Control | 适用家庭/课节/动作、暂停原因、来源、生效及恢复条件、版本 | 结构化查询；普通咨询、改期或日期变化不自动解除暂停 |
| Operation | operation_id、动作/目标/最终内容、关联Event与要求、content_basis、幂等键、真实阶段、发生/确认时间、原始回执 | 草稿不是交付；未知先核实；原回执不覆盖新要求 |
| Message与Memory | 原消息、实际回复、覆盖关系、个性化证据根、摘要、纠正/失效关系、同步状态 | 未答输入不被摘要吞掉；摘要不是新增学习证据 |

Event的业务状态采用pending、in_progress、waiting、done、cancelled；执行器的领取/运行租约另存，不把进程运行状态当业务目标完成。update_pending是协调标记，不是第六种业务状态。

waiting保存reason、resume_condition、可空review_at及时间来源。无review_at仍纳入每日恢复；内部复核时刻不能冒充家长约定。独立期限和必要交付部分可作为Event内明细保存，不能只存一个下一步而丢掉其他责任。

必要交付部分应在原范围内补足；新独立服务必须留到daily。当天新增一个步骤不等于允许新增一个目标，后端检查目标身份和允许字段，语义边界另用模型用例验收。

## 3. 运行接口与权限

| 接口（拟议） | 调用者 | 合同 |
| --- | --- | --- |
| run_daily(family_id, business_date) | 08:00调度/同任务恢复 | 创建或恢复唯一daily运行；装入全量责任与确定性事实；可新增/同目标合并 |
| submit_service_progress(report) | 服务运行；其原操作结果补齐器 | 先持久化报告及关联原事项，再排队progress；不能夹带新Event |
| run_progress(report_id, revision) | 报告处理器 | 仅允许改报告关联的原Event；校验后提交，确认精确报告版本 |
| record_pending_planning(input) | 服务 | 保存独立新后续需求，供下一daily消费，不授予当天发送资格 |
| apply_control(change) | 服务经后端校验 | 明确暂停立即生效，保存来源和范围，返回真实提交回执 |
| claim_existing_step(now) | 程序调度器 | 从当天已有条目派生执行资格；等待、暂停、待更新、已领取不重复派发 |
| prepare/dispatch/reconcile_operation | 执行适配器 | 按最终动作校验发送，先记录操作身份，未知查询原操作 |

只有daily权限可创建正式Event和当天成员。Planner输出是提议，后端实际实施权限、字段白名单、来源检查、版本比较及持久提交；不能只靠提示词禁止新增。

服务角色没有修改正式规划的工具，只能报告进展、保存待规划需求和已获支持的即时约束。Planner没有直接对外发送工具。家庭范围和工具权限由程序绑定；R05家庭内部更细权限矩阵继续暂缓。

## 4. 调度与两个入口

程序承担08:00触发、候选步骤选择、等待条件检查、来信入库、操作核实、服务窗口与重启恢复。它不需要每次扫描都调用LLM。

- **daily**：每日08:00一次有效提交。相同家庭/业务日有唯一成功标识，失败重试沿用身份；停机恢复不能重建同义目标。
- **progress**：只有已有事项的新服务报告触发。服务根据新事实/结果报告；无变化的核验不反复报告。
- 回执先保存原操作事实，必要时补齐原报告的revision并继续同一progress流程；任意回调不能直接发起新规划。
- 学情同步只保存数据、覆盖时间和程序指标；迟到批次不再次daily。原事项按其核验步骤取得新事实后可报告，新候选次日评估。
- 截止T停止派发新的常规外发，真正发送前再次检查当前时钟。后台仍接收和保存消息、回执，处理原报告；日终没有无条件Planner调用。

当天未列入主动范围的旧Event可以更新来信带来的进展，但不因更新自动加入主动队列。明确由当次来信要求、可当次完成的服务正常进行；新的后续安排进入待规划记录。

## 5. 提交、失败与跨日恢复

模型/网络在事务外运行；同家庭的状态应用在短事务内执行。提交校验输入版本、适用约束和允许事项范围，原子保存Event、原计划条目、报告消费与提交回执。

相同report_id/revision重复提交返回原结果；同身份不同载荷拒绝。旧解释被更正或替代后不可恢复执行。若还有更新报告未处理，旧报告完成不能清空update_pending。

daily会读取未处理报告。08:00时按同家庭提交顺序处理：先消费或明确吸收已入库进展，再形成日清单。提交记录精确覆盖的报告版本；较晚到达的报告继续progress，不能被旧daily覆盖或“顺带消费”。

首版保留保守版本冲突重评，无关更新的精细依赖优化R10延后。过期或无效输出保留责任、报告和失败原因，可有限重试并暴露人工处理入口；不能无限忙等或自动结案。

相关Event待更新时暂缓重复主动派发，普通独立答疑、必要澄清、原操作查询仍可进行。模型处理失败不撤销已保存的暂停，已完成的真实操作也不因收尾失败丢失。

重启/跨日扫描未完成Event、未答消息、未消费报告、待规划输入、未知操作及记忆同步缺口。原ID、原期限、等待、暂停和历史保留；不批量补发旧窗口消息。

## 6. 交付、完成与改约校验

delivery型按建立时约定的内容、对象、要求和已确认交付阶段判断；goal型按原业务目标判断。提醒成功可以完成“这次提醒动作”，不能把“完成补课”Event结案。学习已完成但具体时刻未知时，核实时间与完成时间分开。

最终文案中的答疑、催课、邀请、交付等动作都要检查，不只沿用最初路由标签。新来信、适用暂停、报告待处理、过期草稿、未知同义操作和服务截止会影响资格；内容修改后重新检查。文字与动作声明一致仍需语义验收。

超时未知先核实原操作，单次not_found不证明可安全重发。已发送历史永远保存；迟到回执是否满足当前要求另判，旧错误内容不能关闭更正后的责任，纯期限变更不必作废内容。

简单改约可嵌在Event.proposed_change：提议送达不代表生效。需要确认的改约，只有适用的有效接受才能替换期限，同时更新Event、原计划条目与定时索引，保留旧期限和逾期历史；不自动解除暂停。

## 7. Skills与上下文接入

三类配方详见上下文文档：service、planner_daily、planner_progress。普通回复不运行预规划阶段；无需强制ServiceBrief，服务读取提交后的Event与可选service_hint。

后续适配plan-proactive-service的daily/progress两种范围，调整close-service-case为整理真实结果和进展报告，不能默认结案。补课Skill中的“规划”是当前服务方法，不具有后台创建Event的权限。

完整加载Skill及其必读规范，真实读取适用知识，工具权限按角色配置。本轮没有修改这些文件或运行配置；不把设计中的接入写成已加载。

以下A01—A34逐字保留原场景和期望，用于避免简化架构时遗失业务责任。它们是验收目录，**并非宣称全部实现，亦不要求首批一次启用全部服务能力**。

| 适用组 | 编号 | 执行时机 |
| --- | --- | --- |
| 核心调度、状态、操作与个性化 | A01—A08、A13—A16、A25—A28、A30—A34 | V1后端闭环必测；按两个入口解释 |
| 对话、知识、记忆和服务边界 | A09、A10、A18—A24 | 对应首批Skill/知识接入时必测，不以后端测试替代 |

| S04 | 反馈实际发送成功；补课提醒实际发送成功 | 前者满足原发送标准才完成，后者目标仍未完成 |
| S05 | 家长说生病，随后问课程入口，Planner暂时失败 | 暂停即时生效，正常答疑；补课等待、退出执行队列且跨日保留 |
| S06 | 同一报告重复/乱序，旧报告更新期间出现新报告 | 精确版本幂等；新进展不被覆盖或错误解除待更新 |
| S07 | 白天提出独立后续需求，要求今晚完成 | 保留原要求和剩余工作，说明尚未安排；不承诺自动次日交付、不偷加事项 |
| S08 | 定时扫描或学情同步无变化 | 不直接调用Planner；原步骤核验得到新进展才报告 |
| S09 | 原发送未知，迟到真实回执 | 关联原操作并补齐原服务报告；不重发、不新建任意规划入口 |
| S10 | 等待无准确review_at；连续两日无来信 | 每日仍恢复该责任，不遗忘、不自动催促或结案 |
| S11 | 08:00学情未齐，稍后到齐 | 使用明确覆盖范围，不凭旧数据认定失约、不再次daily新增 |
| S12 | 改约提议送达、无关回答、有效接受依次到来 | 原期限保留至有效接受；提交后同步原条目/计时索引并保留历史 |
| S13 | 截止前生成草稿，截止后才准备发送 | 常规新外发被拦；未答消息、报告、待规划与未知操作继续保存 |
| S14 | 08:00规划读取后又到来进展，两个提交交错 | 序列化提交并重新校验，精确消费报告，不覆盖新进展或重复执行 |

S01—S14均为待执行用例。固定脚本、结构校验、真实模型、真实数据库/故障、真实渠道分别记录结果，不相互替代。

## 11. 开发和验收顺序

1. **冻结输入合同**：对齐系统提示词初稿、uid数据样本、确定性规则、角色权限和完成标准，输出可校验schema。
2. **实现持久记录与调度**：Event/DailyPlan/报告/待规划/操作，08:00入口、原步骤执行、窗口与恢复，用可控数据验证状态。
3. **接入两个模型角色**：三个上下文配方，daily与progress工具权限，完整Skills和真实知识读取。
4. **跑跨日服务闭环**：一个虚构家庭经历发送型反馈、补课提醒、生病等待、普通答疑、新需求待规划及次日合并延续。
5. **加入可控故障验收**：模型无效输出、重启、重复消息、相关新暂停、未知/乱序回执、改约和更正，执行对应A/S用例。
6. **接受控真实渠道**：业务数据、服务窗口、渠道回执及人工接续具备后，再记录真实家庭试运行证据。

交付物应区分设计、代码、自动检查、实际模型/数据库运行、真实渠道及人工业务验收。当前仅完成设计更新，未开展上述后端实现或本版验收。
