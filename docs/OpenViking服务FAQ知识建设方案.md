| 直播测评与报告 | 直播入口、回放、测评、报告含义 | 直播场次、测评安排、真实学习记录 |

先以8个主题作为编辑结构，最终线上文件数按实际核实内容生成，不为凑数发布空文档。服务阶段作为条目标签，同一个问题可适用于多个阶段，避免在“开课前”和“全程通用”重复写答案。

不预设去重后必须剩多少条。归并条件是“相同意图、相同适用条件、相同答案”；问题相似但政策条件不同的，保留条件分支。一次问题涉及两件事时可关联两个条目。

## 一个问题如何维护

业务人员主要维护以下内容，来源定位、哈希和机器索引由加工程序生成。问题编号稳定，移动主题或调整问法时不改变；删并后的编号保留重定向。

| 字段 | 内容 |
| --- | --- |
| 问题编号和主问题 | 如FAQ-SERVICE-BOOK-001，是否需要另购纸质原著 |
| 常见问法 | 必须另外买纸质书吗、原著需要自行准备吗；“礼盒里是不是原著”另属礼盒内容问题，可关联但不强行归为同义问法 |
| 适用条件 | 已知级别、产品形态、服务阶段；涉及权益时补订单类型与活动，涉及入口时补客户端版本；未知填未知 |
| 回答要点 | 可核实的结论和完整条件，区分事实、一般建议及可调整话术 |
| 关联依据 | 产品或课程稳定编号、规则或物料地址，以及原稿行号；没有依据就明确标待核实 |
| 所需信息与服务动作 | 如需查订单、物流或暂停状态；关联现有Skill名称，不杜撰工具名 |
| 缺口处理 | 哪一部分暂不能确认、需补哪项资料、可先回答什么 |
| 维护状态 | 待核实、可发布、已替代或已停用；确认人、生效时间、替代关系 |

发布状态和使用条件分开：可发布的FAQ也可能需要查询订单后才能回答；待核实内容不能因为语义匹配分数高就变成可用政策。

例如“我的礼盒发了吗”，标准条目可以维护如何区分课程随材、活动礼品和第三方购书订单，以及相应查询入口。它不能维护“已经发货”这个答案。后者由当次真实查询结果填入。没有工具时只给已确认的自查路径或转交待办，不能宣称已查询、已催单或已提交。

对“为什么课程不附原版书”，产品权益是引用依据；商业或版权原因若未经确认不保留为确定解释。对“孩子是不是学会了人物卡片”，FAQ只能指向判定所需作品和适用课节，不能仅凭完课或通用范例作结论。

## 与产品知识和Skill的连接

同一产品事实只设一个维护来源。产品知识中的课程定位、分级、功能，FAQ引用相应稳定编号，不另写一套可独立修改的政策。现有产品8个FAQ可并入统一问题索引，但正文仍由原产品资料维护。

为了让问题条目可独立理解，可以在生成正文时带入必要的简短依据与适用条件。该摘要必须记录来源修订，来源改变时重新生成或暂时停用依赖条目；不是再建立一份人工独立维护的答案。

来源发生冲突时，先核对它们是否针对同一对象与时期。产品文档并不天然胜过FAQ，文件更新得晚也不自动覆盖旧政策。未确认的部分保留缺口；两份待核实资料互相引用不算业务确认。

一般解释使用`answer-course-service-question`；具体课程问题接续`explain-lesson`；效果疑虑接续`address-learning-concern`；退款申请与投诉接续`handle-complaint-escalation`；依据缺失使用`follow-up-unanswered-question`。本次不新增这些Skill，也不调整它们的运行权限。

云端拟使用`viking://resources/digitaltutor/faqs/reading-camp/<revision>/`。默认调用只访问选定修订的已发布正文；原始话术、未解决冲突、审核说明和历史价格不放入该线上目录。发布正文内必须保留适用条件、版本、来源状态和需查实时信息的提示。

目录摘要说明能回答哪些问题，概览列问题编号、常见问法和适用限制，正文保留每个问题完整内容。以主题文件为初始导入单位；沿用课程和产品任务已验证的CLI导入、读回和导航维护方式。若具体主题正文过长或召回不佳，再按自然子主题拆分，不按固定字数切断条件与答案。

8份文件不保证优于更多文件。要观察同义问题能否找到、无关内容是否挤占结果以及正文读取成本。当前原表3.81万字符，增加条件后可能变长，不能直接套用产品5份短文的测试结论。

建议运行时按以下顺序使用：

1. 从当前问题和已知上下文形成查询，补充已知课程级别与必要条件；不为普通操作问题强制先查订单。
2. 已知问题编号时直接定位正文；否则在选定FAQ修订内检索，首轮可试取3个候选主题。跨主题问题分别检索，按问题编号去重。
3. 读取命中问题的完整正文与条件。一级摘要只用来定位；本地段落编号由接入层解释，不能假设OpenViking原生支持任意Markdown锚点读取。
4. 按需继续读取产品、课程或规则依据；查订单和业务状态由现有工具层负责。未确认适用性时，只追问影响答案的关键条件。
5. 根据有效依据回应，或接续相应Skill。记录问题编号、知识修订、使用的事实和剩余缺口。

`faq-index.json`是接入层的索引，不会自动成为OpenViking语义索引。首版把主问题和精选别名放进主题正文与导航，让仅使用CLI的智能体也能找到；本地索引用于精确定位和去重。只有实测显示别名召回不足，才考虑增加纯问题导航资源，避免一开始把同样答案再索引一遍。

目录和标签只是筛选手段，不是访问控制。业务状态、适用条件与工具权限由应用负责；OpenViking不能替代这些判断。

## 加工与验证安排

第一步，抽取309条原始记录，保留问题、答案、阶段、级别、行号和源文哈希。做问题归并和8主题分类，并产出逐条去向映射。原稿中答案仅是追问或确认语的条目，记录为追问线索，不伪装成完整FAQ答案。

第二步，对比现有产品和课程资料，形成可引用内容、新增知识候选及待核实项。优先核实直播回放期限、赠书权益、电子物料权限、活动有效期和退款政策；不自行生成企业制度。AI来源标记不消失，核实通过的条目另记确认依据。

第三步，只把满足发布条件的内容生成线上正文；其余保留在本地维护清单。原稿中的具体家庭称呼、金额、已执行状态和不适当评价不作为通用事实发布。个体对话回流时先去标识，再由业务核实形成共享知识。

第四步，通过服务器现有CLI导入隔离修订，逐份读回正文、检查摘要与导航，保留任务和检索回执。入库后才将可用地址交接给Skill接入方；当前直接读取原表的入口需要届时替换，不能只新建知识库却继续让生产答疑读取整张原表。

第五步，用固定问题分别验证检索和回答。建议第一轮32题：8个主题各2个不同问法，共16题；另16题覆盖条件变化、冲突、查状态和动作请求。测试问题应在查询前固定，保留业务人员后补的未见问法，减少只用原表原句的自测偏差。

| 重点测试 | 正确行为 |
| --- | --- |
| 新报不赠书，老学员询问赠书 | 识别条件分支，不用单一通用答案覆盖 |
| 月课家长问是否48周240节 | 不把L2年课配置套给月课 |
| 主课和直播回放分别能看多久 | 区分对象；期限未核实则说明缺口 |
| 想要原著PDF或练习册PDF | 区分物料和可用授权，不根据模糊“电子版”统一回答 |
| 已经请假，为什么还催课 | 关联原事项、查暂停及触达，处理后续安排，不能只道歉 |

分别记录：相关主题是否召回、目标条目是否找到、适用条件是否正确、是否取到完整依据、是否应查询或转人工、是否虚构承诺、状态是否真实写回。知识缺口的正确结果可以是待核实，不以“每题都直接回答”为目标。检索通过不等于老师智能体端到端通过。
