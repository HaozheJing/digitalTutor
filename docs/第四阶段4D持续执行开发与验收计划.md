## 2. 保持的架构与业务合同

1. 保持Hermes原生AIAgent循环、两角色三配方、原Scheduler/Worker和唯一持久JobQueue。daily的基线/日内接纳仍由宿主绑定范围；progress仅处理绑定报告及原事项，不新增目标、擅自增加联系成员或全量重排。不得修改vendor以绕过业务问题，不建第二队列或通用工作流引擎。
2. Planner安排，Service答疑、执行、核实并提交实际报告。自然语言结束文本不自动外发；内部复核不获得家庭发送权。家长新问题不因原事项等待或Planner失败而失去答复资格。
3. `completion_condition`有值时保留原说明，空时由Service依据原请求和实际结果自主判断并保存assessment。goal仍需原课节可信完成证据；delivery仍需原对象、要求版本、全部必需part及实际回执。提醒、登记、安排确认、草稿和模型自述均不能替代完成。
4. 暂停限制相关触达，不自动取消学习目标；改约须有原提议、实际送达和有效接受依据。新增日期或行动约束不能被“同目标”归并抹去；提议、含糊接受和实际承诺分别记账。
5. 准备、派发、回执和业务完成分别记录。unknown沿原operation核实；确认unknown与交付unknown各自保留，不借另一条回执结清，也不换request_id或文案获得新发送机会。
6. 保留家庭串行、来信让行、版本/租约核权、触达预算、暂停和发送窗口。用户接受约115秒的稍晚发送，仅作为已知非阻断表现；`before/window`上界及北京时间08:00≤发送时刻<21:00不放宽，`execute_at`不改称精确送达承诺。
7. 本轮多部分交付使用原方案明确的两项文字义务：先发参与情况回顾，再发文字建议。无需新增图卡、语音或媒体生成。既有事项若必须交付图卡/语音而工具不可用，保留缺项与原标准；文字不冒充必须媒体完成。
